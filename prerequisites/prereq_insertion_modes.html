Insertionmodes

An insertion mode is not a rendering state, a tokenizer state, or a CSS concept. It is one thing only: which table of rules the parser currently consults to decide what to do with the next token.

P4

What a "state" actually is here

Picture a government office building where every visitor (token) has to be processed at a desk, and there are ~20 desks, each staffed by a clerk who only knows one specific rulebook. "Insertion mode" is just which desk the parser is currently sitting at. Walking a visitor to a different desk mid-processing — because their paperwork turned out to need a different rulebook — is a mode switch. It doesn't change the visitor. It changes which rulebook gets consulted next.

Crucially: the current desk is a single global variable. There's exactly one "current insertion mode" for the whole parser at any instant — it is not per-element, not stacked (that's what the stack of open elements, P3, is for), just one name.

§13.2.4.1 defines the insertion mode as parser state consulted by "tree construction dispatcher" every time a token needs processing. Modern HTML Standard (2025+, after the <select> mode removal covered in Track 1 Module 12) lists these:

Five modes are marked YES — and if you look closely, they are exactly the five elements from Track 1 Module 04's fostering list, each with its own mode named after it (tbody/thead/tfoot share "in table body"; table itself is "in table"). That is not a coincidence — a mode exists because that element's children need special handling, and the table-family modes' special handling is, at bottom, foster parenting.

Crazy detail

A mode switch and a token dispatch are two different operations that happen to often occur together. "Reprocess the token" — which shows up constantly (in column group, in table text, the fragment-parsing algorithm) — means: switch modes, then run the exact same token again through the new mode's rules, without consuming a new one from the tokenizer. This is why a single input token can be "seen" by more than one mode's rules before it's finally consumed.

How this differs from the tokenizer's states

The tokenizer (P1) has its own, much larger state machine (~80 states: data state, tag open state, RAWTEXT state, …) that governs how raw characters become tokens. That machine is invisible from here on — this course's engine implements only enough tokenizer behavior to correctly emit the six token shapes from P1. Insertion modes are a completely separate, much smaller state machine that consumes those tokens. Conflating the two is one of the most common confusions in this subject — worth flagging now so it doesn't resurface in Module 01.
