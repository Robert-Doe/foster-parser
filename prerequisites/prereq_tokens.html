Prerequisite P1

Tokens

A tokenizer's whole output vocabulary is five shapes. Tree construction — everything this course is about — never sees raw text. It only ever sees one of these five.

P1

The five token kinds

Think of the tokenizer as a court stenographer, not a judge. It doesn't decide what markup means — it just chops the character stream into labeled slips of paper and passes them, one at a time, to whoever's making decisions downstream (that's tree construction, starting at Module 00).

  1. DOCTYPE — <!DOCTYPE html>. Carries a name, and public/system identifiers (almost always all empty in modern HTML).
  2. Start tag — <table>, <tr id="x">. Carries a tag name, an attribute list, and a self-closing flag.
  3. End tag — </table>. Carries a tag name only — attributes on an end tag are a parse error and are discarded by the tokenizer before tree construction ever sees the token.
  4. Comment — <!-- ... -->. Carries the comment data as one string.
  5. Character — a single character of text. Not a run of text — the tokenizer emits one character token per character. (Module 08 depends on this: it's why "in table text" has to buffer a whole run itself.)

Plus one sentinel that isn't really a token but is handled identically by every insertion mode's dispatch table: end-of-file.

Watch it

"Character token" being per-character, not per-run, surprises people who assume the tokenizer does the batching. It doesn't — batching (when it happens at all) is tree construction's job, and it only happens in exactly one insertion mode. See Module 08.

What our engine's token objects look like

// track1-core/00_tokens_and_nodes/src/tokens.js — the whole vocabulary
{ type: 'DOCTYPE',   name, publicId, systemId, forceQuirks }
{ type: 'StartTag',  tagName, attrs: Map, selfClosing }
{ type: 'EndTag',    tagName }
{ type: 'Comment',   data }
{ type: 'Character', data }      // one character
