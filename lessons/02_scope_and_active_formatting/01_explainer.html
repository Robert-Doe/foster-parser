Scope &Active Formatting Elements

Built four modules apart, on purpose — but they're the two halves of one mechanism the real spec calls the adoption agency algorithm. This page puts them next to each other.

01

The Big Analogy

Scope (Module 13) is a rule about which doors an END TAG's key can reach. The active formatting elements list (Module 10) is a standing guest list that gets consulted on INSERTIONS, not departures. They read like they should be opposites — one gates exits, one triggers entries — but the real spec's adoption agency algorithm (which this course doesn't build) is specifically the machinery for when BOTH matter on the same end tag at once: an end tag whose target isn't simply "the current node," but is buried under other still-open elements the naive scope-and-pop logic (this course's Module 13) can't resolve on its own.

02

The Mechanism — where each one actually lives

Scope (Module 13, built on Module 04's five-element derivation): a read-only question about the STACK OF OPEN ELEMENTS — "walking down from current node, do I hit `target` before I hit a wall?" Table, `td`, `th`, and a handful of others are walls. This is what stops a stray `

` inside a `` from reaching an outer `

Active formatting elements (Module 10, gated by Module 02's predicate): a separate list, mutated on insertion and on specific clearing operations (table cleanup pops the STACK without touching this list — the entire mechanism behind the triple-`` example). This is what makes a formatting element get silently, correctly RECREATED after table cleanup severs it from the stack.

Where they'd meet, if this course built it: the adoption agency algorithm processes an end tag (like a misnested `` or ``) by searching the ACTIVE FORMATTING LIST for a matching entry, then checking that entry's relationship to the STACK — using scope-adjacent reasoning to decide how to restructure the tree. It is, in effect, "scope's boundary logic, applied to formatting-list entries instead of literal end-tag targets, with a tree-restructuring step Module 13 never needed." Track 1 stops short of building this — see Module 10's concept_adoption_agency.html for exactly where the line is drawn.

03

Why four modules apart, on purpose

The pedagogical reasoning

Module 02 (the gate) and Module 04 (the five elements) had to come early — everything in Track 1 depends on them. Module 10 (active formatting elements) needed Module 05's full insertion-location algorithm to exist first, since reconstruction's whole point is that recreated elements get fostered too. Module 13 (scope) needed nothing from Module 10 at all — it's built entirely on the stack (Prerequisite P3) and the five-element derivation (Module 04), with zero dependency on the formatting list. Placing it last was a sequencing choice, not a dependency requirement — see this cluster's own reason for existing: two mechanisms that never call each other in this course's code, but that any reader building toward a full implementation needs to see as two faces of one larger algorithm.
