The Noah's ArkClause

Module 10 built reconstruction without it, honestly, because no test needed it. This page explains what it's actually for — and does the arithmetic on why the spec's authors thought it was worth a special case.

01

The Big Analogy

Two of every kind boards the ark; the third and every subsequent one is turned away. The active formatting elements list has the same rule: if three entries since the last marker already share the same tag name, namespace, and attribute set, the EARLIEST of the three is evicted the moment a fourth would-be match tries to join. Not because a fourth matching entry is wrong, exactly — but because letting the list grow without bound turns a cheap, routine check (reconstruction, run before nearly every insertion) into an expensive one.

02

The Mechanism, and the arithmetic

"Push onto the list of active formatting elements" first checks whether three entries since the last marker already match the new element's tag name, namespace, AND attributes (compared as they were at parser-creation time, unordered). If so, the earliest of the three matching entries is removed before the new one is pushed. The spec names this the Noah's Ark clause and notes it's three per family, not two.

Why it matters for cost, not just correctness: reconstruction (Module 10) walks the list backward from the end every time it's invoked, and — in the worst case, when nothing on the list is already on the stack — recreates every entry it walked past. Input like <b><b><b><b>… (some malformed or adversarial markup does exactly this) would, without the Ark clause, grow the list without bound, and EVERY subsequent character insertion's reconstruction call would walk and potentially recreate an ever-growing chain — turning what should be a cheap per-token check into work that scales with how many <b> tags appeared earlier in the document. With the clause capping same-family entries at three, that walk is bounded no matter how many <b> tags the source contains.

Why this course didn't build it

Module 10's own test case (the spec's canonical triple-<b> example) only ever has ONE <b> entry on the list at a time — nowhere near the three-in-a-row threshold that would trigger eviction. Building the clause would have been code with no test able to exercise it, which is exactly the kind of speculative addition this course's engineering conventions warn against. It's real, it's well-motivated, and it's absent — all three of those are true at once, and Module 10's DECISIONS.md says so directly rather than pretending the gap doesn't exist.
