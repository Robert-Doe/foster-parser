01

The Big Analogy

A sanitizer that removes a <script> tag by scanning the SOURCE STRING for it, then re-serializes what's left, is trusting that the tree it scanned and the tree a browser will eventually build from its OUTPUT are the same tree. Every module in Track 1 is a catalog of ways that assumption can be false — not because the sanitizer author made an arithmetic mistake, but because tree construction has more relocation tactics (Module 12's atlas) than casual intuition accounts for, and every one of them can change which element ends up as the parent of attacker-controlled content.

02

The Mechanism — three concrete seams, named plainly

Seam 1 — foster parenting reshapes ancestry (Modules 02–09). A sanitizer that allow-lists "content inside a <td> is safe because a <table> can't execute anything" is reasoning about markup BEFORE parsing. After parsing, content the author thought was safely trapped inside table structure may be sitting OUTSIDE it entirely, as a sibling of the table, in whatever element happened to be its parent before the table was opened — a completely different, possibly unvalidated, context.

Seam 2 — reconstruction duplicates elements silently (Module 10). A sanitizer that counts occurrences of a tag in the source, or that assumes "one <b> tag, one <b> element" as an invariant for some later transformation, can be handed a tree with MORE elements of that tag than the source ever wrote — each one independently a target for attribute-based attacks (an event handler attribute, for instance) if the sanitizer's per-element checks aren't re-run against every reconstructed copy.

Seam 3 — scope silently drops end tags (Module 13). A sanitizer's own bookkeeping (e.g. a stack it maintains itself, tracking "am I currently inside an allowed context") can drift out of sync with the REAL parser's stack if it doesn't independently implement scope's wall behavior — an end tag the sanitizer's bookkeeping thinks closes something may be silently ignored by the actual parser, leaving the sanitizer's model of "what's currently open" wrong for everything that follows.

The through-line to mXSS

Mutation XSS (mXSS) — Track 2's actual subject — is precisely the class of bug that lives in these seams: a payload that is inert, or looks inert, in one representation (the string a sanitizer scanned) but becomes live once a browser's real tree-construction algorithm — the one this course spent thirteen modules building a working model of — gets to reparse it. None of Track 1's modules were built AS attacks; they're the parser behaving exactly as specified. mXSS is what happens when a security boundary is drawn using an approximate mental model of that same, correctly-specified behavior.

03

Limits — what this page does NOT claim

Not claimed here

  • That any specific sanitizer library has any specific vulnerability — no library is named or tested on this page
  • That Track 1's engine has been used to construct a working exploit — that's Track 2's job, with real code and real verification

Claimed here

  • That the three seams named above are real, general mechanisms this course's own Track 1 modules built and verified against real browsers
  • That they are the right shape of thing to worry about when reasoning about sanitizer correctness — which is exactly the hypothesis Track 2 tests directly
