The Full Mode-CollapsingDecision History

Every place this course's engine merged real spec modes together, in the order it happened, with the reasoning re-stated and the eventual cost tallied.

1

Module 05 — the founding decision

Module 05's dispatch5.js needed to reach a nested-table test case (<table><td><table><tr>FOO</table></table>) that requires <td> and <tr> handling. Building real in table body/in row/in cell modes for this one case would have meant three new mode tables for a single test. Instead, <td>/<tr> insertion stayed nominally in "in table" mode, with the stack's own current-node identity — not the mode name — doing the work that would otherwise require the extra modes.

Justification at the time: Module 02's gate (isFosterParentingTarget) checks current node identity directly. A <tr> current node fosters; a <td> current node doesn't — regardless of what the engine calls the mode it's nominally in. Module 05's own test (FOO correctly fostered from a <tr>, correctly NOT fostered from a <td>, in the same real parse) is direct proof this reasoning held for that case.

2

Module 08 — independent re-confirmation

Module 08's buffering (in table text) runs whenever a Character token arrives in "in table" mode — with no check for whether the real spec would be in in table, in table body, in row, or in cell at that exact moment. Its own DECISIONS.md re-derives, independently of Module 05, that this is safe: buffering delays *when* a character gets inserted, never changes *what the current node is* when it finally does, so the gate's answer is unaffected either way. Two modules, two different features, the same underlying argument holding both times — evidence the collapsing decision was structurally sound, not just lucky once.

3

Module 11 — where the argument finally breaks

Module 11 needed a <template> containing a <tr>. Real spec: entering a template pushes a NEW mode-dispatch context (in template) whose <tr> rule sends straight to in table body — skipping "in table"'s own tbody-implying step entirely. This engine's collapsed model has no such skip available: everything still funnels through the SAME "in table" handling that implies a tbody whenever current node isn't already tbody-ish, because that's the only handling that exists. Result: an extra, spurious <tbody> a real browser doesn't produce.

The Module 05/08 argument ("current node identity is all that matters") is still TRUE here, as far as it goes — the foster-parenting gate still answers correctly. What breaks is a completely different piece of logic (the tbody-implying rule) that, unlike the gate, genuinely does depend on which of the collapsed modes you're "really" in — a distinction this engine threw away three modules earlier.

Crazy detail

Module 11 didn't undo the collapse — undoing it would mean building a real in template mode-dispatch stack, a genuinely new piece of machinery. Instead, it changed its OWN test input (from a bare <tr> to an explicit <tbody>) to sidestep the one rule that needed the distinction, verified the substitute case against a real browser first, and documented the avoided case by name. A three-module-old architectural decision, still net-positive everywhere else, produced one specific, nameable gap — and the fix was scoping around it honestly rather than either patching over it silently or re-architecting three modules of already-verified code.
