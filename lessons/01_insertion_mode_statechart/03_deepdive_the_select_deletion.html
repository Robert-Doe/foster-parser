The Select ModeDeletion

This course removed three modes for pedagogical reasons. The real HTML Standard removed two modes for a completely different, shipping-browser reason — in 2024–25, not as a hypothetical.

1

The Big Analogy

This course's mode collapsing (deep dive 1) was a construction shortcut, taken once, up front, for a building nobody else will ever occupy. The real spec's in select/in select in table removal is a wing of a building actually in use by billions of people, demolished and rebuilt while people were still walking through it — because the old wing's rules ("almost nothing can go inside a <select> except <option>/<optgroup>/<hr>") turned out to be actively blocking a feature (stylable, rich-content <select> elements) that browser vendors wanted to ship.

2

The Mechanism

Per this course's own Module 12 atlas row and the attached reference course's own Module 12: the in select and in select in table insertion modes have been removed from the current HTML Standard entirely. The motivation was the customizable/stylable <select> work (appearance: base-select) — the old parser discarded almost every tag inside <select> other than <option>, <optgroup>, and <hr>, which made rich <select> UI unmarkupable no matter what CSS shipped alongside it. Removing the dedicated modes lets ordinary content through; the one behavior worth preserving — a nested <select> start tag acting as an implied </select> — was reimplemented as a stack-traversal check borrowed from how <button> already handled the analogous case.

Why this belongs in a mode-collapsing deep dive specifically

The outcome for foster parenting barely changed: <table><select><option>x still fosters the <select> to just before the table, and the <option> still ends up inside it — but it used to happen because a dedicated insertion mode captured the tokens, and now happens because the current node is a select, and select simply isn't one of the five foster-parenting elements (Module 04). An entire pair of insertion modes was deleted from a shipping spec, and the foster-parenting behavior fell out UNCHANGED — the strongest possible confirmation, from a much higher-stakes context than this course's own engine, that the rule keys on current-node identity per insertion, never on which mode happens to be active.

3

Limits — what this deep dive does NOT claim

Not claimed

  • That this course's engine implements either the old or new <select> behavior — neither is built (Module 12's atlas, honestly)
  • That every mode-collapsing decision is this safe — deep dive 1 documents a case (Module 11) where an analogous collapse genuinely cost something

Claimed

  • That a real, shipping specification change independently confirms this course's central architectural bet (current-node identity, not mode name, is what matters for fostering)
