Track 2 · Module T2-02 · Defensive / educational

Naive SanitizerBreak

A sanitizer that reasons about SOURCE STRING position instead of the actual parsed tree. Right by accident sometimes. Wrong — completely, silently, attacker-controllably wrong — other times. Same logic, every time.

What this module proves

"This tag is textually between <table> and </table>, so it must be contained" is true for <input type=hidden> and false for a plain <img> — the exact same reasoning, two opposite outcomes, and the attacker picks which one you get.

01

The Big Analogy

A mailroom clerk decides which packages are "internal, already-screened mail" by checking whether the sender wrote "Building B" somewhere in the packing slip — never opening the box, never checking where the package actually got routed once it entered the building. Most of the time this correlates with something true. It is not, itself, a fact about where the package ends up. A clerk relying on it is trusting the SENDER's claim, not the BUILDING's actual routing — and the sender is exactly who you can't trust.

02

What Happens, Step by Step

  1. isTrustedBySourcePosition(html, tagIndex) finds <table> and </table> in the raw string and checks whether a given tag's string index falls between them.
  2. scanWithNaiveHeuristic regex-scans for tags carrying a (stand-in) dangerous attribute and reports which the heuristic would trust.
  3. Case A: a plain <img> — the heuristic trusts it (it's textually inside the table tags). Track 1's real engine shows it actually fosters OUTSIDE the table (Module 06's established behavior).
  4. Case B: an <input type=hidden> — the SAME heuristic trusts it, for the same reason. This time the real engine shows it genuinely DOES stay inside (Module 07's established behavior).
  5. Conclusion: the heuristic's correctness depends entirely on which of Track 1's element-specific rules the attacker's chosen tag happens to fall under — not on anything the heuristic itself understands.

04

The Code, Explained

The entire naive heuristic:

function isTrustedBySourcePosition(html, tagIndex) {
  const tableStart = html.indexOf('<table');
  const tableEnd = html.indexOf('</table>');
  return tagIndex > tableStart && tagIndex < tableEnd;
}

Note what it never does: parse anything, ask what the current node will be, or consult Module 04's five-element list or Module 07's explicitly-handled-cases table. It's a fact about a string, presented as if it were a fact about a tree. Full rationale, including why Case B is essential to this module's argument (not just a second bug), is in DECISIONS.md.

07

Brain Exercise

Could the naive heuristic be "fixed" by adding a special case for every tag Module 07 says refuses to foster (style, script, template, hidden input, form)?

That would make Case B's correctness principled instead of accidental — but it wouldn't fix the underlying design flaw, only patch this specific symptom. The heuristic would still be reasoning about SOURCE POSITION rather than the actual tree, and Track 1's later modules (10's reconstruction, 11's template-content redirection) show there are element-creation paths — a formatting element re-created by reconstruction, content redirected into a template's `.content` — where "textually between two tags" and "structurally contained by them" diverge in even more ways than the plain fostering case this module demonstrates. Patching known cases one at a time is exactly the losing game T2-04's defense (verify the REAL tree, not assumptions about it) is built to avoid entirely.

08

There Are No Dumb Questions

Is a source-position heuristic like this a realistic thing anyone would actually build, or a strawman?

Realistic — string-based HTML manipulation predates widespread DOM-based sanitization by years, and ad hoc "is this substring inside that tag" logic still shows up in template engines, log scrubbers, and hand-rolled content filters that were never designed with an adversarial parser-behavior model in mind. The specific heuristic here is constructed for this course, but the CLASS of mistake — trusting source-text position as a proxy for tree structure — is exactly the mistake Heiderich et al.'s original mXSS research (cited in REFERENCES.md) documented in real, shipped sanitizers.

Why does this module reuse Module 06 and Module 07's already-verified tree shapes instead of re-checking them against a live browser again here?

Because this module isn't making a new claim about tree shape — Track 1 already established, and verified, exactly where `` and `` end up in a table. This module's new claim is entirely about the SANITIZER's behavior: does its heuristic agree with those already-established facts? Re-verifying the tree shape again here would test something already tested; DECISIONS.md points back to exactly where each reused fact came from.
