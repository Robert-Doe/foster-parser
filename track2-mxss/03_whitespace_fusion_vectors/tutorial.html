Track 2 · Module T2-03 · Defensive / educational

Whitespace &Fusion Vectors

"java". "script:alert(1)". Checked separately, both clean. Combined by nothing more exotic than Track 1 Modules 08 and 09 doing exactly what they were built to do — and never checked again after combining.

What this module proves

A sanitizer that validates text as it arrives — a real, common pattern for streaming or incremental checks — can be hand two chunks that individually pass a javascript:-prefix filter, and end up with a single fused text node reading exactly "javascript:alert(1)", never re-checked.

01

The Big Analogy

Airport security scans two separate carry-ons, both clear. What nobody checked is what happens after both bags are combined into one, once they're past the checkpoint and repacked together on the other side. Nothing about either bag was hidden or disguised — the combination itself is what the checkpoint's process never had a chance to examine, because the examination happened before the combining did, not after.

02

What Happens, Step by Step

  1. "java" is inserted ordinarily into a <div>, before any table exists.
  2. A <table> is opened. Current node becomes table — a fostering target (Track 1 Module 04).
  3. "script:alert(1)" arrives as a run of Character tokens while current node is table — Module 08 buffers it, then flushes it with fostering enabled, since it contains non-whitespace.
  4. The flushed run lands, per Module 05's location algorithm, immediately before the table — which is exactly where "java"'s TextNode already sits.
  5. Module 09's fusion (unchanged, no special-casing) merges the two into ONE TextNode: "javascript:alert(1)".
  6. A checker validating each chunk AS IT ARRIVED never sees this combined string — only a checker re-run against the final tree does.

04

The Code, Explained

The naive check, and the one that should replace it:

// what a naive incremental sanitizer does — checks each piece as it shows up:
function checkChunksIncrementally(chunks, dangerousPattern) {
  return chunks.map(chunk => ({ chunk, flagged: dangerousPattern.test(chunk) }));
}

// what it needs to do instead — check the REAL, FINAL text, after fusion:
function checkFinalText(finalText, dangerousPattern) {
  return { text: finalText, flagged: dangerousPattern.test(finalText) };
}

Note that neither Module 08 nor Module 09 needed to change at all to produce this outcome — full rationale, including why this module re-verifies against a live browser despite reusing Module 05's already-proven mechanism, is in DECISIONS.md.

07

Brain Exercise

Would splitting the dangerous string across THREE chunks instead of two (e.g. "java", "scr", "ipt:alert(1)") make this attack harder to pull off?

Not fundamentally — it would need one more fostering-eligible insertion point (e.g. two separate table-adjacent boundaries) to arrange, but Module 09's fusion accumulates ANY number of consecutive fostered/adjacent text insertions into one node, not just two. The number of chunks is a question of how much markup structure the attacker needs to arrange to create enough separate insertion events; it doesn't change the underlying gap a per-chunk checker has.

08

There Are No Dumb Questions

Isn't "check text incrementally as it streams in" just a bad design generally — why would a real sanitizer do this?

It's a reasonable design under a very common, very different threat model: validating chunks as they arrive over a network stream, before the whole document is even available, to reject obviously-bad content early and cheaply. That's a legitimate engineering tradeoff for THAT problem. It becomes a security gap specifically when the same incremental check is treated as sufficient FINAL validation, skipping a proper end-of-parse re-check — the mistake isn't building an incremental check, it's not also building the final one.

Why is this module's DECISIONS.md careful to re-verify the "javascript:alert(1)" fusion against a real browser, when Module 05 already proved the identical mechanism works for "abcdef"?

Because "the mechanism works for one string" and "the mechanism works for THIS security-relevant string" are different claims this course's own standing rule (never assert unverified behavior) treats as distinct — the string content itself is never part of what makes fusion fire, but re-checking anyway, rather than assuming, is exactly the discipline this whole course has modeled since Module 00's first assertion.
