Track 2 · Module T2-01 · Applied layer · Defensive / educational

What mXSSActually Is

Not a new parser bug. The same, correctly-specified tree construction Track 1 spent thirteen modules building — pointed at a piece of code that assumed the tree would look like the source markup suggested.

What this module proves

An <img> tag placed inside a <table> — exactly where a template author put it — ends up, after ordinary parsing, as the table's sibling, not its descendant. Fully attributed. Structurally invisible to any inspector that only walks table > tbody > tr > td.

01

The Big Analogy

A guard checks IDs at the door of a specific room, confident that everyone who came to the party is somewhere inside that room, because that's where the invitations said to go. What the guard doesn't know is that the building's own layout — nothing anyone snuck past, nothing anyone tampered with — quietly redirects a specific category of guest to the hallway instead, before they ever reach the room's door. The guard's checklist is airtight for the room. The hallway was never on the checklist.

02

What Happens, Step by Step

  1. User-controlled content — an <img> tag with an inert marker attribute standing in for a dangerous one — is placed inside a <table>, inside a wrapper <div id="sandbox">.
  2. This exact input is parsed with Track 1's own, already-verified dispatch13 engine, unchanged.
  3. A "narrow inspector" walks only table > tbody > tr > td — the shape a template author would reasonably expect user content dropped into a table to have.
  4. A full walk of the whole #sandbox subtree runs separately, for comparison.
  5. The <img> is fostered (Track 1, Modules 02–09) to land as a sibling of the table — found by the full walk, found by nobody doing the narrow one.

The Code, Explained

The assumption, made concrete as code — and exactly where it goes wrong:

function collectFromAssumedTableCells(tableElement) {
  const found = [];
  for (const tbody of tableElement.children) {
    // Assumes: everything the user could have injected is somewhere
    // under here. Track 1 Modules 02-09 are the reason that's false.
    if (tbody.tagName !== 'tbody') continue;
    /* ...tr, td... */
  }
  return found;
}

07

Brain Exercise

The narrow inspector would have caught this <img> if it also checked direct children of #sandbox, not just table cells. Does that mean the fix is "walk one level higher"?

It fixes THIS specific example, but not the general problem — which is exactly why Track 2 continues rather than stopping here. "Walk one level higher" is still an assumed-shape check; Module 05's own nested-table example (<table><td><table><tr>FOO</table></table>) shows fostered content can land arbitrarily deep inside unrelated structure, not just "one level up." The only inspector that can't be out-maneuvered this way is one that walks the ENTIRE resulting tree, unconditionally — which is a real, buildable defense (T2-04), not a bigger assumption.

08

There Are No Dumb Questions

Why does this course keep saying "structural claim" instead of just showing a working alert() popup — wouldn't that make the danger more convincing?

The tree-shape fact — a node lands somewhere an inspector didn't check — is the entire technical content of the vulnerability class. Whether a specific attribute on that node happens to be one a specific browser executes is a separate, orthogonal fact about browser behavior, not about parsing, and demonstrating it would require constructing something that actually runs in a browser context — which this course won't do, on principle, regardless of how contained the demonstration would be. The structural proof is complete without it.

Is this a bug in the HTML parser?

No — worth stating as plainly as possible. Every module in Track 1 verified this engine's behavior against real, unmodified browsers; foster parenting is specified, intentional, and has existed in this form for over a decade specifically to make malformed table markup produce a deterministic, sane tree instead of undefined behavior. The "bug," if there is one, lives entirely in code that reasons about markup without accounting for what a spec-compliant parser actually does with it.
