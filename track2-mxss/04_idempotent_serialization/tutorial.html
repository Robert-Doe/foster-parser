Track 2 · Module T2-04 · The defense

Idempotent SerializationDefense

Not a fix for foster parenting specifically. A general check — parse, serialize, reparse, compare — that catches T2-01 through T2-03's attacks without knowing any of their names, because it doesn't trust any representation of a tree except the tree a real, independent parse actually produces.

What this module proves

A tree built via direct DOM mutation (table.appendChild(textNode) — exactly the shortcut Track 1 Module 11 warned about) fails this check outright; a tree built by real parsing passes it cleanly. No false alarms, no missed catches, on either of this module's test cases.

01

The Big Analogy

Instead of a guard trying to anticipate every hallway a visitor might slip into (T2-01's narrow inspector), or trusting a claim about where someone already is (T2-02's source-position heuristic), or checking people one at a time as they enter (T2-03's incremental checker) — this guard does something structurally different: takes a snapshot of the whole building's current occupancy, has the ENTIRE building rebuilt from scratch based on that snapshot, and compares the new building to the old one, room by room. If anything is in a different room the second time, something about the first snapshot wasn't trustworthy as a description of a stable building — full stop, no need to know why.

02

What Happens, Step by Step

  1. serializeToHTML(node) — new in Track 2 — turns a tree back into an HTML string, the direction Track 1 never needed.
  2. checkIdempotent(rootNode, reparseFn) serializes rootNode, reparses that exact string via reparseFn (real tree construction), and compares both trees structurally via canonicalize.
  3. Case A builds a tree via direct DOM-mutation-style insertion — table.appendChild-equivalent, bypassing "appropriate place for inserting a node" (Prerequisite P5) entirely, exactly as Track 1 Module 11 warned real DOM mutation does.
  4. The check catches it: reparsing the serialized string fosters the text out, disagreeing with the original tree.
  5. Case B builds a tree via real parsing (no shortcuts) and confirms the check reports it stable — no false alarm on legitimately correct content.

04

The Code, Explained

The whole defense, in one function:

function checkIdempotent(rootNode, reparseFn) {
  const serialized = serializeToHTML(rootNode);
  const reparsedRoot = reparseFn(serialized);
  const before = canonicalize(rootNode);
  const after = canonicalize(reparsedRoot);
  return { stable: before === after, before, after, serialized };
}

Building this module's own reparse step surfaced a real bug: Track 1 never handles an explicit <tbody> tag (only ever an implied one) — full story, and the additive fix, in DECISIONS.md.

05

Limits — What You Cannot Do Yet

Can't do yet

  • Automatically FIX an unstable tree — this module only detects instability, matching a real "reject or re-sanitize" decision point, not a repair
  • Handle serialization edge cases beyond this module's own test input (attribute quoting, void elements) — serializer.js is deliberately minimal

Can do

  • Correctly flag a tree assembled via direct DOM mutation as unsafe to serialize and hand off
  • Correctly clear a tree that was always built by legitimate parsing, with zero false positives on this module's test cases

07

Brain Exercise

This check catches Case A because reparsing moves the text node. Would it catch an attack where the SECOND parse produces a tree with the exact same SHAPE, but a dangerous attribute value that only appears after some transformation neither parse alone would reveal?

No — and this is a real, important boundary of what this defense covers. canonicalize compares tag names and text/attribute values structurally; if both parses produce identically-shaped trees with identical values, the check reports "stable" correctly, because the two representations genuinely do agree. This defense catches disagreements BETWEEN two representations of the same content — it says nothing about whether a single, self-consistent representation is itself dangerous (that's what T2-01/T2-02/T2-03's specific pattern checks are for, run separately). Idempotent-serialization checking and pattern/allowlist checking are complementary, not substitutes for each other.

08

There Are No Dumb Questions

Is this actually what real sanitizers like DOMPurify do, or a simplified teaching version?

The core idea — verify that a "cleaned" tree survives a serialize-and-reparse round trip unchanged, and treat instability as a signal to reject or re-sanitize — is the real pattern documented in DOMPurify's own approach and the academic mXSS literature this course cites (REFERENCES.md). This module's implementation is deliberately minimal (a small serializer, a structural diff) to make the mechanism legible, not a claim of feature-parity with a production library.

Why does this module's own bug (the explicit <tbody> gap) matter for trusting the defense itself?

Because a defense that produces FALSE POSITIVES on legitimately safe content is nearly as harmful as one that misses real attacks — false positives get "fixed" by developers turning the check off, which then misses everything. Catching and fixing this bug before shipping the module's own DECISIONS.md is the same discipline this course has applied since Module 01's DOCTYPE bug: verify against real output, don't assume the code is right just because it looks right.
